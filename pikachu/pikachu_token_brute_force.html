Pikachu - 暴力破解 - Token 防爆破

# Pikachu # Web # Token # Burp Suite # Session

一、题目信息

  • 题目名称：token 防爆破？
  • 题目路径：Pikachu → 暴力破解 → token 防爆破？
  • 题目方向：Web - 登录 Token 与 Session 校验
  • 题目环境：本地部署，PHP 7.4.33 + MariaDB 10.11.19 + PHP 内置服务器
  • 访问地址：http://127.0.0.1/pikachu/vul/burteforce/bf_token.php
  • 验证账号：admin / 123456
本文只记录本机 Pikachu 靶场实验，不针对任何未授权系统。会话 Cookie 和 Token 示例均不作为真实凭据使用。

二、源码分析

页面表单中包含一个隐藏的 Token 字段：

<input type="hidden" name="token" value="..." />

服务端接收登录请求后，先比较客户端提交的 Token 和当前 Session 中的 Token：

if($token == $_SESSION['token']){
    if($line_pre->execute()){
        $line_pre->store_result();
        if($line_pre->num_rows > 0){
            $html .= '<p> login success</p>';
        }
    }
} else {
    $html .= '<p> csrf token error</p>';
}

Token 的生成逻辑位于 inc/function.php：

function set_token(){
    if(isset($_SESSION['token'])){
        unset($_SESSION['token']);
    }
    $_SESSION['token'] = str_replace('.', '', uniqid(mt_rand(10000, 99999), true));
}

页面末尾调用 set_token()，因此每次响应结束后，当前 Session 中的 Token 都会更新。下一次请求必须使用最新 Token。

三、Burp / DevTools 验证

  1. 访问题目页面，保持当前浏览器会话。
  2. 在 Elements 中找到 input[name="token"]，记录当前 Token。
  3. 提交一次错误 Token，观察返回：
<p> csrf token error</p>

这说明服务端先拒绝了请求，尚未进入用户名和密码校验。

重新加载页面获得最新 Token，再提交错误密码：

POST /pikachu/vul/burteforce/bf_token.php HTTP/1.1
Cookie: PHPSESSID=<current-session>

username=admin&password=wrong&token=<current-token>&submit=Login

返回：

<p> username or password is not exists～</p>

这说明 Token 校验已经通过，请求进入了账号密码校验。

四、登录验证

在同一会话中使用最新 Token 和本地测试账号：

username=admin&password=123456&token=<current-token>&submit=Login
返回 <p> login success</p>，验证成功。

五、Token 与 Session 的关系

测试条件结果说明
错误 Tokencsrf token errorToken 与 Session 不匹配
正确 Token + 错误密码账号或密码错误已通过 Token 校验
正确 Token + 正确密码login success登录成功
旧 Token 重放Token 校验失败页面响应后 Session Token 已更新

PHPSESSID 标识当前 PHP 会话，Token 保存在该会话中。只复制 Token 而不携带对应 Cookie，或者使用其他会话的 Cookie，都不能通过校验。

六、结论与修复建议

  • Token 可以防止跨会话伪造和旧请求重放，但必须使用安全随机数，并设置合理的有效期。
  • 登录请求应维护 Session Cookie，并获取与当前会话匹配的最新 Token。
  • Token 不能替代登录限速、失败次数限制、账号锁定和强密码策略。
  • 实际系统还应避免使用可预测的 uniqid() 作为安全 Token，改用密码学安全随机数。

七、总结

本题通过一个隐藏表单字段展示 Token 校验流程。判断响应时，应先区分 Token 校验失败和账号密码校验失败，再使用 Burp 的请求详情观察 PHPSESSID、token 与表单参数之间的关系。
