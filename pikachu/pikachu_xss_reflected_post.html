Pikachu - 反射型 XSS（POST）

分类：Web / XSS · 环境：本机 Pikachu 靶场 · 题目路径：Cross-Site Scripting → 反射型 xss(post)

仅在自己部署的 127.0.0.1 靶场练习；测试代码只弹出数字，不读取或发送任何数据。

一、登录题目

打开 /pikachu/vul/xss/xsspost/post_login.php，使用 admin / 123456 登录。登录成功后页面跳转到 xss_reflected_post.php，并通过 Cookie 判断登录状态。

这里先用错误密码测试，页面返回 username or password error!；再使用正确密码登录，确认题目流程正常。

二、普通 POST 回显

在输入框提交 test123，页面显示：

who is test123,i don't care!

这说明输入来自 POST 请求体中的 message 参数，而不是地址栏查询字符串。POST 只改变了数据传输位置，不会自动提供 XSS 防护。

三、源码与漏洞成因

题目源码直接把 $_POST['message'] 拼入 HTML：

if (isset($_POST['submit'])) {
    if ($_POST['message'] == 'kobe') {
        $html .= "<p class='notice'>愿你和{$_POST['message']}一样，永远年轻！</p>";
    } else {
        $html .= "<p class='notice'>who is {$_POST['message']},i don't care!</p>";
    }
}

服务端没有进行 HTML 输出编码，因此攻击者可以提交 HTML 标签。浏览器解析响应时，会把标签当成页面结构，而不是普通文本。

四、构造与验证

提交下面的无害测试载荷：

<script>alert(1)</script>

请求体示例：

message=%3Cscript%3Ealert%281%29%3C%2Fscript%3E&submit=submit

本地验证结果：

  • 错误密码被拒绝，正确账号可以进入题目页面。
  • test123 被原样反射到响应 HTML。
  • <script>alert(1)</script> 被原样保留在响应 HTML 中，证明输入未被转义。
  • 提交内容位于 POST 请求体，地址栏没有 message 查询参数。

在浏览器中提交该载荷时会弹出内容为 1 的提示框；这只用于确认脚本执行，不涉及 Cookie 或其他数据。

五、修复思路

输出到 HTML 文本节点时，应使用对应上下文的编码：

$message = htmlspecialchars(
    $_POST['message'],
    ENT_QUOTES | ENT_SUBSTITUTE,
    'UTF-8'
);
$html .= "<p class='notice'>who is {$message},i don't care!</p>";

修复后，浏览器只会显示 <script>alert(1)</script> 这段文字，不会创建并执行脚本。不要把 POST、输入框限制或前端校验当成服务端 XSS 防护。
