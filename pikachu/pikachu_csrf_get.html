Pikachu - CSRF（GET）

分类：Web / CSRF · 环境：本机 Pikachu 靶场 · 题目路径：Cross-site request forgery → CSRF(get)

仅在自己部署的 127.0.0.1 靶场练习。示例只修改测试账号资料，不针对任何真实站点。

一、正常流程

打开 /pikachu/vul/csrf/csrfget/csrf_get_login.php，使用题目提示的测试账号登录。登录后进入 csrf_get.php，点击“修改个人信息”进入 csrf_get_edit.php。

二、源码与成因

编辑表单使用 GET 提交：

<form method="get">
  <input name="sex">
  <input name="phonenum">
  <input name="add">
  <input name="email">
  <input type="submit" name="submit">
</form>

服务端只检查当前 Session 是否登录，然后直接使用 GET 参数更新当前用户资料，没有 CSRF Token、Origin/Referer 校验或再次确认。

三、构造请求

登录状态存在时，可把正常编辑请求改造成链接：

http://127.0.0.1/pikachu/vul/csrf/csrfget/csrf_get_edit.php?sex=boy&phonenum=10000000000&add=csrf-test&email=csrf%40example.test&submit=submit

诱导仍处于登录状态的用户访问该 URL，浏览器会自动携带当前 Session Cookie，服务器便会把请求识别为该用户自己的修改操作。

四、漏洞判断

  • 攻击者不需要知道受害者的密码或 Session 值。
  • 攻击者只需构造一个可访问的 GET 链接。
  • 用户未登录或 Session 已失效时，请求会被重定向到登录页。
  • GET 被用于有副作用的更新操作，是本题最直观的风险信号。

五、修复思路

修改资料应使用 POST，并为每个会话生成不可预测且一次性的 CSRF Token；服务端验证 Token 后再执行更新。还应设置合适的 SameSite Cookie，并校验 Origin/Referer 作为额外防线。仅把 GET 改成 POST 不能单独解决 CSRF。
