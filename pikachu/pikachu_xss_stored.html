Pikachu - 存储型 XSS

分类：Web / XSS · 环境：本机 Pikachu 靶场 · 题目路径：Cross-Site Scripting → 存储型 xss

仅在自己部署的 127.0.0.1 靶场练习；测试脚本只弹出数字，不读取或发送数据。

一、功能观察

访问 /pikachu/vul/xss/xss_stored.php，页面是一个留言板。提交内容后，留言会写入数据库，随后在“留言列表”中展示。与反射型 XSS 不同，这里的输入不会只停留在当前响应中，而是会影响之后打开留言板的用户。

二、源码与成因

服务端只对输入做了数据库层面的转义，然后直接把查询结果拼进 HTML：

$message = escape($link, $_POST['message']);
$query = "insert into message(content,time) values('$message',now())";

// 读取后直接输出
echo "<p class='con'>{$data['content']}</p>";

escape() 主要用于避免 SQL 字符串破坏，并不会把 HTML 标签编码成普通文本。数据被保存后，输出位置又缺少 HTML 上下文编码，因此构成存储型 XSS。

三、构造与验证

  1. 在留言框提交无害测试载荷：
<script>alert(1)</script>
  1. 刷新页面或重新访问留言板。
  2. 观察留言列表，数据库中的内容被原样放入页面结构；浏览器会把 script 当成脚本解析。

本地验证时应关注两个阶段：提交请求是否成功写入，以及后续 GET 页面是否再次输出该字符串。第二阶段才是存储型 XSS 的关键证据。

四、影响范围

只要其他用户访问包含恶意留言的页面，脚本就可能在其浏览器中执行。实际影响取决于页面权限、Cookie 属性和站点功能。本文只使用 alert(1) 进行执行验证，不读取 Cookie 或提交数据。

五、修复思路

在输出到 HTML 文本节点时进行编码，而不是只依赖写入数据库时的转义：

$content = htmlspecialchars(
    $data['content'],
    ENT_QUOTES | ENT_SUBSTITUTE,
    'UTF-8'
);
echo "<p class='con'>{$content}</p>";

同时应对富文本场景使用经过审计的白名单清洗器，并在删除、管理后台等相关页面保持同样的输出编码策略。
