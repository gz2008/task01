Upload-Labs Pass-13：POST save_path 与 NUL 截断边界

Upload-Labs Web File Upload 路径参数 PHP 8.4

Pass-13 先检查 multipart 文件名是否以 jpg、png 或 gif 结尾，然后把 POST 参数 save_path 和随机文件名拼接成最终路径。这里同样存在“校验值”和“实际使用值”分离的问题。

验证边界：当前 PHP 8.4.24 下，带真实 NUL 字节的保存路径返回 HTTP 500，上传目录没有生成 PHP 文件。旧版 PHP 的截断效果没有被用来冒充当前环境的成功。

一、源码与信任边界

$file_ext = substr($_FILES['upload_file']['name'],
                    strrpos($_FILES['upload_file']['name'], ".") + 1);
if (in_array($file_ext, array('jpg','png','gif'))) {
    $img_path = $_POST['save_path']."/".rand(10, 99).date("YmdHis").".".$file_ext;
    move_uploaded_file($_FILES['upload_file']['tmp_name'], $img_path);
}

save_path 没有做目录规范化，也不要求必须位于上传目录内。经典利用依赖旧版 PHP 在 NUL 字节处终止字符串，使路径前缀变成类似 ../upload/pass13_probe.php。

二、当前环境复现

测试在 multipart 的 save_path 值中放入真实 0x00，文件部分仍使用合法 PNG 名称：

save_path = ../upload/pass13_probe.php + 0x00
filename  = pass13_probe.png
Content-Type = image/png

请求结果：

HTTP_STATUS=500

随后按精确前缀检查上传目录，没有出现 pass13_probe* 文件。白名单已经通过，失败发生在文件系统路径处理阶段。

三、为什么现代 PHP 不再截断

PHP 5.3.4 以后修复了文件系统路径中的 NUL 截断。当前 PHP 8.4 会拒绝包含空字节的路径，因此经典技巧失效。这并不代表源码的路径控制问题是安全的：如果攻击者能改变 save_path，仍要检查目录穿越、覆盖范围和异常字符。

四、修复建议

  • 上传目录必须由服务端固定配置，不能来自请求参数。
  • 保存前规范化路径，并验证真实目标仍在允许目录内。
  • 拒绝 NUL、换行、路径分隔符和平台特殊字符。
  • 使用服务端随机文件名和固定安全扩展名。

五、复盘

Pass-13 可以从两个层面记录：第一，源码确实把可客户端控制的路径用于写文件；第二，当前 PHP 8.4 环境拒绝了历史 NUL 截断请求。前者是代码设计问题，后者决定本次实验是否取得可执行文件。
