二、通用分析顺序

  1. 先查看 URL 参数、POST 字段、Cookie 或请求头，确定用户输入从哪里进入。
  2. 用永真、永假或单双引号判断注入类型：数字型、单引号型、双引号型或带括号型。
  3. 根据页面反馈选择读取方式：有回显用 UNION，有报错用 updatexml，只有真假差异用布尔盲注，只有时间差异用时间盲注。
  4. 最后读取 database()、version()、information_schema 或业务表数据，验证注入确实影响数据库查询。
URL 编码：在浏览器地址栏中，# 会被当作 URL 片段，复现时通常写成 %23；-- - 中间的空格也不能省略。POST、Cookie 和请求头注入可用 Burp Repeater 或脚本直接发送。

盲挑战的压缩读取思路

Less-62 至 Less-65 不直接显示查询值，但页面会根据 row['id'] 从固定用户名数组中取一个元素。可以把目标数据切成 8 字节块，用 HEX、CONV 和 LPAD 转成固定长度的十进制串，再把每一位作为联合查询的第一列返回。数组下标 0-9 会分别对应不同用户名，因此每次响应都能稳定还原一个十进制数字。

-- 结构示例：逐位返回十进制数字
id=0') union select
  CAST(SUBSTR(LPAD(CONV(HEX(SUBSTR((SELECT secret_col FROM challenges.random_table),1,8)),16,10),20,'0'),1,1) AS UNSIGNED),
  2,3-- -

24 字符的随机 key 可切成 3 个 8 字节块，每块最多 20 位十进制数字，总计 60 次请求即可还原；挑战关的 130 次额度足够完成。该方法比按字符做 6-7 次二分判断更省请求。

九、实际漏洞根因

  • GET、POST、Cookie 和请求头进入 SQL 后直接字符串拼接，没有参数绑定。
  • 错误信息暴露数据库结构，使 updatexml/extractvalue 可以直接带出数据。
  • 堆叠查询接口使用支持多语句的 mysqli 调用，使一次输入可以执行第二条写操作。
  • 第二阶注入把转义后的内容存入库中，却在后续 SQL 中重新拼接，导致存储阶段安全、使用阶段失守。
  • 宽字节场景中数据库连接字符集与转义函数不一致，使反斜杠被错误吃掉。

十、修复与复盘

  1. 所有业务输入使用 PDO/mysqli 预处理语句，不拼接 SQL。
  2. 数字型参数做整数转换；字符串参数绑定类型并限制长度。
  3. 数据库连接、页面字符集和输入编码必须一致，不能只依赖转义函数。
  4. 关闭生产环境的数据库错误回显和 PHP 详细错误。
  5. 数据库账号遵循最小权限，禁止 FILE、堆叠查询和不必要的跨库访问。
  6. 对用户输入在“写入”和“读出后再次使用”两个阶段都进行类型约束，避免第二阶注入。

本次练习的核心收获是把每一关拆成三个问题：输入从哪里进入、SQL 的包装是什么、页面能提供哪种反馈。确定这三点后，报错、联合查询、盲注或堆叠查询只是不同的证据通道。
